# i18n (next-intl) — guía para agentes de extracción

Infra montada: next-intl 4.x, locales `en` (default, sin prefijo), `es`, `pt` (`/es/...`, `/pt/...`).
Sin auto-redirect por Accept-Language (`localeDetection: false`, pedido SEO). El switch de idioma es manual vía UI.

## Estructura

```
i18n/routing.ts        # defineRouting: locales, defaultLocale, localePrefix "as-needed"
i18n/navigation.ts     # Link, redirect, usePathname, useRouter, getPathname (locale-aware)
i18n/request.ts        # getRequestConfig: carga y mergea los namespaces por locale
lib/i18n/seo.ts        # localeAlternates(path) → hreflang para metadata
middleware.ts          # createMiddleware(routing), excluye /api, /_next, /_vercel y archivos
messages/{en,es,pt}/   # un JSON por namespace
app/[locale]/          # TODAS las páginas viven acá; app/ raíz solo api/, globals.css, icons
```

Namespaces (top-level keys de `messages`): `common`, `nav`, `footer`, `home`, `booking`, `services`, `wc`, `fleet`, `pages`, `blog`. Cada uno es un archivo `messages/<locale>/<ns>.json`. Agregar keys ahí; NO crear namespaces nuevos sin actualizar `i18n/request.ts`.

## Reglas

1. **Links internos**: importar `Link` (y `usePathname`/`useRouter`/`redirect`) desde `@/i18n/navigation`, nunca desde `next/link` / `next/navigation`. El `href` se escribe sin prefijo (`/transfers`) y next-intl agrega `/es`/`/pt` solo.
2. **Toda página nueva** bajo `app/[locale]/` arranca así (Next 15: `params` es Promise):

```tsx
export default async function FooPage({
  params,
}: {
  params: Promise<{ locale: string }>;
}) {
  const { locale } = await params;
  setRequestLocale(locale); // habilita SSG; siempre ANTES de usar getTranslations
  ...
}
```

3. **Server components** (default): `const t = await getTranslations("services");` de `next-intl/server`, o `useTranslations("services")` de `next-intl` en componentes sync.
4. **Client components**: `useTranslations("booking")` de `next-intl`. Ya reciben messages vía `NextIntlClientProvider` en `app/[locale]/layout.tsx` (v1: viajan todos los messages al client — al extraer los párrafos largos de services, evaluar filtrar qué namespaces se pasan al provider).
5. **JSON**: keys anidadas por sección, ICU para plurales/interpolación (`"hours": "{count, plural, =1 {1 hour} other {# hours}}"`). Headings con markup → `t.rich("title", { em: (c) => <em>{c}</em> })`.

## Ejemplo real: traducir un heading

`messages/en/home.json`:
```json
{ "hero": { "title": "Where Luxury Travel Begins" } }
```

En el componente (`components/sections/Hero.tsx`, server):
```tsx
import { getTranslations } from "next-intl/server";
const t = await getTranslations("home");
<h1>{t("hero.title")}</h1>
```

## SEO / hreflang

`lib/i18n/seo.ts` exporta `localeAlternates(path)` — devuelve `{ languages: { en, es, pt, "x-default" } }` con URLs absolutas `https://relier.com`, prefijo as-needed (en sin prefijo) y trailing slash. `x-default` apunta a la versión EN.

Patrón por página (ver `app/[locale]/page.tsx` como referencia viva):

```tsx
import { localeAlternates } from "@/lib/i18n/seo";

export const metadata = {
  alternates: localeAlternates("/transfers"),
};
```

Con `generateMetadata` (páginas con canonical propio, ej. blog):

```tsx
export async function generateMetadata({ params }: PageProps): Promise<Metadata> {
  const { slug } = await params;
  return {
    alternates: {
      canonical: `https://relier.com/${slug}/`,
      ...localeAlternates(`/${slug}`),
    },
  };
}
```

⚠️ NO poner `localeAlternates` en el layout: metadata de layout se hereda y todas las subpáginas quedarían con hreflang del home. Va por página.

## Verificado

- `npm run build` → todas las páginas SSG (●) por locale; `/` = EN sin prefijo, `/es/`, `/pt/` prerendereadas.
- `/api/*` no pasa por el middleware.
- El copy sigue 100% en EN — la extracción a `messages/` es el paso siguiente.
